# 前端视觉系统落地方案 v1.0

> 状态：待实施。本文是开发与验收依据，不代表已完成代码迁移。
>
> 设计基准：[UI 风格规范](../../../UI_STYLE_GUIDE.md) · [薄荷工作台参考图](./reference-overview.png)

## 1. 目标与范围

目标是在**不改变现有页面结构和业务交互**的前提下，使桌面端界面更统一、更精致、更容易人工维护：

- 统一颜色、字体、间距、边框、圆角、阴影、控件高度及交互状态。
- 将重复的基础控件样式收敛到少量可复用组件，而不是在页面中继续拼接长串 Tailwind 类。
- 保持浅色、深色及全部 accent 主题一致，保证键盘操作和弹层行为。
- 先通过小范围试点确定视觉方向，再按模块推广；每次改动可独立测试和回退。

非目标：重排页面、改动数据任务 DSL 或运行逻辑、替换 XYFlow 画布、Glide Data Grid、CodeMirror，或同时升级 React/Tailwind 主版本。不能为追求组件统一而改变字段选择器、筛选条件树、多选标签等业务行为。

## 2. 技术决策

采用 **shadcn/ui 的 Radix 版本作为基础组件源码参考**，只引入本项目确实需要的组件，并将源码纳入 `src/renderer/components/ui/` 维护。shadcn/ui 不是一套必须全局接管样式的运行时组件包；其组件源码可由项目直接调整。当前项目已经使用 React 18、Tailwind 3、Radix Select/DropdownMenu/Switch 和 Lucide，因此不需要在本轮引入另一套完整组件体系。官方说明现有 React 18/Tailwind 3 项目可继续使用；新项目虽然默认选 Base UI，Radix 版本仍受支持。

- [shadcn/ui 介绍](https://ui.shadcn.com/docs)
- [React 18 / Tailwind 3 兼容说明](https://ui.shadcn.com/docs/tailwind-v4)
- [Base UI 默认、Radix 仍受支持](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)

实施约束：

1. 在独立的 UI 改造分支逐个引入组件，并审查每次生成的文件与依赖变化。不要在现有项目上盲目运行会改写全局 CSS、Tailwind 配置或入口文件的初始化命令。
2. 如使用 CLI，配置 `components.json` 指向 `src/renderer/components/ui/`，明确选择 Radix；记录生成时使用的组件来源和版本。只安装被选中组件实际需要的依赖。
3. 新组件以项目现有语义变量为样式来源，不另建一套独立主题色。生成组件中的颜色类和 `dark:` 类必须经过人工适配后再使用。
4. 基础组件层不得依赖 `electronAPI`、业务数据模型或数据任务 API；业务组件通过 props 组合基础组件。

## 3. 当前代码的关键事实

- `tailwind.config.js` 已把背景、surface、边框、accent、文字和状态色映射到 `src/renderer/styles/globals.css` 的变量；该体系应继续作为唯一颜色源。
- 深色值定义在 `:root`，浅色通过 `.light` 启用；`src/renderer/App.tsx` 切换的是 `.light`，不是 `.dark`。直接复制依赖 `.dark` 的生成样式，会使深色状态失效。**本轮优先适配现有主题机制，不顺带重构全局主题切换。**
- `GlassSelect`、`GlassDropdownMenu`、`GlassSwitch` 已封装 Radix，但触发器、菜单、输入框和按钮的视觉规则仍散落在页面。`data-view/shared.tsx` 和 `input-table-editor-workbench.tsx` 还存在重复的 `InputTableSelect`/`InputTableCheckbox`。
- `SettingsPanel.tsx`、`GlassSelect.tsx` 等仍有 `backdrop-blur` 与半透明面板；这与 UI 风格规范的实底、细边框方向冲突。
- `workflow-forms/shared/` 包含多选字段、标签溢出、表达式和条件相关控件。它们属于业务交互层，不应直接用普通 Select 替换。

## 4. 组件与主题架构

建议目录（按实际引入情况创建，不要求一次生成全部）：

```text
src/renderer/components/ui/
  button.tsx
  input.tsx
  select.tsx
  dropdown-menu.tsx
  dialog.tsx
  switch.tsx
  tabs.tsx
  tooltip.tsx
  badge.tsx
  cn.ts                         # 仅在确实需要合并类名时引入
```

基础组件至少统一以下状态：`default`、`hover`、`focus-visible`、`active`、`disabled`、`error`；按钮额外支持 `loading`，并提供 `primary`、`secondary`、`ghost`、`danger` 四种明确用途。默认控件高度遵循现有 32–36px 规范，图标尺寸、圆角和字重由组件定义，页面只负责布局和业务状态。

生成组件所需语义与现有变量的映射原则如下。优先改写组件类名使用现有 Tailwind token；只有确实缺少的语义才新增变量：

| 新组件语义                   | 现有来源                                           |
| ---------------------------- | -------------------------------------------------- |
| `background` / `foreground`  | `--color-background` / `--color-text-primary`      |
| `card` / `popover`           | `--color-surface`                                  |
| `primary` / `ring`           | `--color-accent`                                   |
| `muted` / `muted-foreground` | `--color-surface-muted` / `--color-text-secondary` |
| `border` / `input`           | `--color-border-muted`                             |
| `destructive`                | `--color-error`                                    |

主色按钮的前景色应作为单独的语义值核对对比度，不能误用现有表示浅色选中态文字的 `--color-accent-text`。所有 accent 主题都必须验证。保留 `prefers-reduced-motion` 行为，不用全局动画遮掩状态变化。

迁移期间用适配层保持现有调用 API：

- `GlassSelect` 保留空字符串值转换、受控打开状态、定位参数和选项禁用语义，内部复用新的 Select 视觉规则。
- `GlassDropdownMenu` 保留 `closeOnSelect`、描述文本和危险操作语义；`GlassSwitch` 保留受控 API。
- `ConfirmDialog` 保留现有 `confirm(): Promise<boolean>` 调用方式；如替换底层 Dialog，需先证明焦点、Esc、遮罩和关闭回调等行为等价。
- `DataToolbarButton`、`DataTableSearch`、两处 `InputTableSelect`/`InputTableCheckbox` 逐步收敛到基础组件；重复实现只能保留一份。
- `workflow-forms/shared/GlassField*` 等业务控件本轮仅复用基础触发器、菜单表面和状态样式，不改变字段搜索、多选、标签计数、键盘选择和数据加载行为。

旧组件名可在过渡期保留；全部调用迁移完成后再统一重命名或删除，避免长期同时维护新旧两套视觉实现。

## 5. 实施阶段与交付物

以下工期是单人开发粗估；以试点验收结果决定是否继续推广。

### 阶段 0：建立基线（0.5–1 天）

- [ ] 确保 UI 改造从可回退的代码状态开始，不与其他功能修改混在同一提交中。
- [ ] 按 UI 风格规范对欢迎页、对话、数据工作台、任务流程、云数据、技能、自动化、API 设置、通用设置建立截图基线；至少覆盖浅色和深色。
- [ ] 重点页面额外记录 1400×900 常规窗口与 800×600 最小窗口；记录一个非默认 accent 主题。
- [ ] 列出高频按钮、输入框、菜单、弹窗、Tab 的现有变体和调用点，标记违反规范的毛玻璃、硬编码主题色及重复实现。
- [ ] 记录构建体积和数据任务画布拖动表现，以便改造后同机比较。

交付物：截图集、控件清单、性能/体积基线和首批迁移文件清单。

### 阶段 1：设计变量与基础组件（2–4 天）

- [ ] 在 `globals.css` / `tailwind.config.js` 中完成必要的语义映射，不复制另一套色值。
- [ ] 建立 Button、Input、Select、DropdownMenu、Dialog、Switch 的首批组件；Tabs、Tooltip、Badge 按试点需求补充。
- [ ] 建立仅供开发使用的组件状态展示页或等价预览方式，集中检查浅/深色、五套 accent、长中文、禁用/错误/加载/焦点状态。
- [ ] 为基础组件增加交互测试：受控值、键盘操作、禁用、打开关闭、焦点恢复及错误状态。
- [ ] 更新 `UI_STYLE_GUIDE.md`，明确新组件的用途和变体，避免页面重新发明基础控件。

退出条件：基础组件在主题矩阵下可用，且没有改变现有页面；`npm run typecheck`、`npm run lint` 和相关测试通过。

### 阶段 2：小范围视觉试点（1.5–2 天）

- [ ] 先迁移 API 设置页和数据工作台工具栏：这两处覆盖常见表单和操作按钮，业务风险低于画布与算子表单。
- [ ] 清除试点区域内与规范冲突的模糊/大面积半透明效果，改为实底、细边框和规范阴影；不改动宽高、分栏及信息顺序。
- [ ] 对照阶段 0 截图进行人工验收；检查长标签、窄窗口、弹层位置和深色主题。
- [ ] 记录试点过程中需要调整的组件 API 和 token，不带着未解决的问题开始全站迁移。

退出条件：试点前后功能等价、视觉方向得到确认，且新增控件样式不依赖页面级覆盖。**未通过时停在试点阶段，不扩大迁移范围。**

### 阶段 3：按模块推广（约 5–8 天）

按以下顺序拆成多个可独立回退的提交或 PR：

1. 应用外壳与对话：侧栏、标题栏、消息区操作按钮、通用确认框。
2. 数据工作台：输入/输出表、任务列表、预览工具栏；合并重复基础控件。
3. 数据任务：节点配置面板和算子表单；保留字段选择、多选标签及条件树的现有行为。
4. 设置、技能与自动化：菜单、表单、状态标签和弹窗统一。

XYFlow 画布、Glide Data Grid、CodeMirror 只调整与新系统接触的外层工具栏、表面和焦点样式，不替换其渲染内核。每完成一个模块立即截图、运行相关测试并评审，不进行一次性全仓替换。

### 阶段 4：全量验收与清理（1–2 天）

- [ ] 在规范列出的九类页面检查浅/深色；基础组件检查全部 accent 主题。
- [ ] 在 800×600 与 1400×900 检查溢出、弹层遮挡、滚动、长中文及缩放后的可读性。
- [ ] 键盘逐项验证 Tab、Enter、Space、方向键、Esc、焦点可见及关闭后焦点恢复。
- [ ] 验证数据任务保存、试运行、字段选择、筛选条件编辑和画布拖动无功能回归。
- [ ] 运行 `npm run typecheck`、`npm run lint`、`npm test -- run` 及构建检查；比较打包体积和同机画布拖动基线。体积或性能明显退化（例如超过基线 10%）必须解释并处理后再合并。
- [ ] 清理不再使用的过渡组件与重复样式；新增用户可见文案必须在中英文资源中同步。

## 6. 完成定义与风险控制

只有同时满足以下条件，才认为本轮视觉系统改造完成：

- 基础控件的颜色、尺寸、圆角、字体、边框、状态由公共组件和 token 统一管理；改造区域无新增硬编码 accent、渐变、毛玻璃或重阴影。
- 现有页面布局和业务交互保持稳定；九类页面完成视觉检查，关键场景有改造前后截图。
- 浅色、深色、accent 换色、窄窗口、键盘交互和弹层定位均通过验收。
- 类型检查、lint、测试及构建通过；画布拖动与数据预览性能没有未经解释的退化。

主要风险及处理方式：

| 风险                                   | 处理方式                                                              |
| -------------------------------------- | --------------------------------------------------------------------- |
| 生成样式与项目 `.light` 主题机制冲突   | 使用现有语义变量适配，不直接照搬 `dark:` 和全局 CSS；逐组件测试深色。 |
| 初始化命令覆盖配置或引入 Base UI       | 明确选择 Radix，只按需引入组件，逐次审查文件与依赖差异。              |
| 通用控件替换导致业务行为变化           | 保留适配层 API；复杂字段选择器只换视觉，不重写交互状态机。            |
| 弹窗、菜单在 Electron 或滚动容器内错位 | 专门验证 Portal、层级、窗口边缘、Esc 和焦点恢复。                     |
| 统一样式影响画布性能                   | 保留 XYFlow/数据网格内核，以阶段 0 同机基线复测。                     |
| 桌面端离线时网络字体不可用             | 检查现有字体回退效果；若视觉不稳定，再单独评估本地字体资源。          |

预期节奏：完成阶段 0–2 后约 **3–5 个工作日**可得到可评审的视觉试点；全站推广粗估 **2–3 周**。工期以组件库存量、试点反馈及交互回归结果调整，不以安装组件库本身作为完成标准。
